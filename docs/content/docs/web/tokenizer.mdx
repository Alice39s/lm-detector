“词表探测”模式和“API”模式共用同一份 API 配置。它不让模型写整数，而是发送一组短文本，从每个响应的 usage 中读取输入 token 数，与 [290 个开源词表归并成的 62 类](../principles/tokenizer.mdx#classes)比对。算法与 CLI 的 `fpd tokenizer` 相同，见[词表探测原理](../principles/tokenizer.mdx)。

## 运行一次探测

### 进入模式 [step]

在检测页选择“词表探测”，或打开 `https://lm.ikale.io/#/?mode=tokenizer`。打开页面、切换模式或修改配置都不会发送请求。

### 开始探测 [step]

点击“开始探测”。每次探测通常发送 8–20 个短请求：先测只含固定包裹的基线，再按当前候选挑选最能区分它们的探针，直到某一类词表或“未收录”的后验概率达到 99%，最后再测一次基线。Messages 协议的每个请求最多输出 16 个 token；其余协议与取样请求一样不设输出上限。

“并行请求”开启时同时发送 4 个探针；关闭后逐个发送，总请求数最少。探测期间可以停止，已完成的探针仍会给出结果。

### 阅读判定 [step]

判定只有三种：

| 判定 | 含义 |
| --- | --- |
| 完全一致 | 所有探针的计数都与某一类已收录词表吻合 |
| 未收录 · 最接近 | 与某一类相近，但有相当一部分探针不同，可能是它的衍生或扩展词表 |
| 未收录的词表 | 与所有已收录的类都无关 |

右侧的百分比是后验概率。候选列表显示前 6 类的“完全一致”概率，最后一行固定为“未收录的词表”。

## 与所填模型核对

所填模型名会与[第一方型号映射](../principles/tokenizer.mdx#api-models)比对，结果显示为以下一种：

- **一致**：测得的词表类与该型号登记的词表相同。
- **不一致**：例如声称 `gpt-5` 却测得 Qwen 词表。
- **尚不能确定**：后验概率还没有集中到某一类。
- **未登记**：映射和别名都没有匹配到该型号，只显示词表判定。

Claude、Grok 等型号登记为“厂商未公开词表”：测得“未收录的词表”算作一致，测得任何已收录的类算作不一致。

<Callout type="warn" title="词表一致只说明分词器相同">
  同一词表常被多个模型复用，例如小米 MiMo 与 MiniCPM-V 复用 Qwen2–Qwen3 词表。中转站若用 tiktoken 在本地估算 usage，也会测成 o200k_base 或 cl100k_base；判定为这两类、且没有确认与所填模型一致时，页面会单独提示这种可能。两次基线计数不同时，页面提示上游加入了会变化的隐藏内容，这次结果不可靠。
</Callout>

## 原始证据

结果区右栏是请求记录：每行显示探针类别、探针原文、输入 token 数和相对基线的增量；失败的请求可以打开错误详情。结果底部有三个折叠项：

- 此类包含的开源词表；
- 各探针的计数表：实测增量、预期增量与是否一致；
- 如何理解词表探测结果。

计数表是原始证据，不是评分解释。

## 导出与离线复算

结果阶段的更多菜单可以导出 JSON。文件与 CLI `fpd tokenizer --output` 同一格式（`fpd-tokenizer-v1`），不含 API Key；用 CLI 的 `--input` 可以按当前词表库离线复算：

```sh
npx lmfpd@latest tokenizer --input fingerpoint-tokenizer.json
```

详见 [CLI 词表探测](../cli/tokenizer.mdx)。
